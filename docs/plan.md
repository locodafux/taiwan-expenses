## 1. Data model

Six tables. Every hardcoded array in the original file becomes a row a person adds or edits in the app.

| Table | Purpose | Key fields |
|---|---|---|
| `households` | One row per couple | `id`, `name` |
| `household_members` | Joins a Supabase Auth user to a household — the only join Row Level Security trusts | `household_id`, `user_id` → `auth.users`, `display_name`, `color` |
| `household_invites` | One-time code so Ann's sign-up joins *your* household instead of creating her own | `household_id`, `code`, `redeemed_by`, `expires_at` |
| `incomes` | Replaces the hardcoded `PAYDAY_TAKEHOME` map (`taiwan-fund-planner.html:426`) | `member_id`, `label`, `amount`, `recurring_day` (1–31), `active` |
| `categories` | Replaces the hardcoded category set (Expenses, Debt, Taiwan fund, Emergency, Savings, Excess…). Fully editable: add, rename, recolor, reorder, archive | `kind` (`bill`\|`fund`), `sort_order`, `rule` jsonb (fund only) |
| `bill_items` | Replaces `EXPENSE_ITEMS` / `DEBT_ITEMS_BY_MONTH` (`:324–355`). Fixed recurring line items inside a `bill`-kind category | `category_id`, `label`, `amount`, `recurring_day`, `end_date` (debt auto-retires) |
| `ledger_entries` | **The real ledger.** One row per (category, occurrence, payday) — for bills, mirrors a `bill_item`; for funds, generated by the allocation engine. Checking it off is the transaction | `category_id`, `bill_item_id?`, `payday_date`, `amount`, `status` (`pending`\|`checked`), `checked_by`, `checked_at` |

**Design call — what "balance" means:** a category's running balance is simply `SUM(amount) WHERE status='checked' AND category_id = X` — no separate balance column to keep in sync, no double-entry bookkeeping. Checking a fund item off (Taiwan fund, savings, a custom goal) **credits** that category's history — the running total that grows toward its goal. Checking a bill off (rent, a debt installment) also credits that category's "paid to date" history. The household's *uncommitted* cash is simply total income posted so far minus every checked entry across every category — one shared pool, several histories. This is my resolution of the brief's "checking off an item deducts from the combined category balance": the deduction is from the shared household pool, and it accumulates into that category's own running total.

**Captain's call — splitting one category by date range** (e.g. Food costs differently 1st–15th vs 16th–end): no schema change needed. A category can hold as many `bill_items` as you like — that's exactly how the original already splits Food into two ₱5,000 entries, one attached to the 5th's payday and one to the 20th's (`:330-331`). In the app, adding "Food (1st half)" and "Food (2nd half)" as two items under the same "Expenses" category — each with its own amount and payday — is the same move; the checklist already groups items by payday, so this reads naturally without true nested sub-categories.

**Validation rule to carry into the UI:** a `bill_item`'s `recurring_day` should be constrained to a day an active income actually lands on — the whole cushion calculation assumes every bill is paid *from* a specific payday's take-home, exactly like the `payday` tag on every expense/debt line in the original (`:325–341`, `:347–353`).

### The allocation engine — reproducing `allocateProportional`

The original algorithm runs in two phases every month:

- **Phase 1 — monthly totals per category**, computed with hardcoded rules: Taiwan fund water-filled to ₱80,000 over 5 months (`:365–391`), Emergency fund gets 30% capped at ₱100,000 with overflow redistributed to Savings/Excess at a 50:20 ratio, Savings gets 50%, Excess gets 20% plus residual (`:398–414`).
- **Phase 2 — per-payday split**, via `allocateProportional(total, weights)` (`:433–450`): each month's total for a category is divided across that month's paydays, weighted by `max(0, leftover)` at each payday (take-home minus that payday's bills and debt), rounded to the nearest peso with the remainder assigned to the payday with the largest weight. Pinatubo — a one-off goal with a hard mid-month deadline — only competes for the paydays that occur before its deadline (`:462–469`); the four recurring funds share the full month's payday set (`:470–484`).

To generalize this for arbitrary user-defined categories, I designed **three rule types** a `fund` category can use (kept in its `rule` jsonb column), applied in tiers so Phase 1 still produces monthly totals the same way, then Phase 2 (the per-payday `allocateProportional` split) runs unchanged:

| Tier | Rule type | Behavior | Reproduces |
|---|---|---|---|
| 1 | `goal` | Target amount + optional target date. Water-fills evenly across the remaining periods until the date, capped by that period's leftover. Stops contributing once the balance reaches target. | Taiwan fund (₱80,000 by Feb), Pinatubo trip (₱15,000, one payday window) |
| 2 | `capped_percent` | Gets a % of what Tier 1 didn't use. If a lifetime cap is set and hitting it would exceed the cap, overflow redistributes to the other percent/remainder categories by weight. | Emergency fund (30%, capped ₱100,000, overflow → savings/excess 50:20) |
| 3 | `remainder` | Splits whatever's left after every Tier 1/2 category, by relative weight. Always sums to exactly the leftover — rounding residue lands here. | Savings (50%), Excess (20% + residual) |

Phase 2 then takes each category's monthly total (from whichever tier computed it) and splits it across the period's paydays using the same `allocateProportional` weighting — unchanged from the original, just fed dynamic incomes/bills instead of hardcoded arrays.

**Captain's call — one field, not three technical presets:** in the app, a fund category has a single optional field, **target amount**. Set it (Taiwan: ₱80,000, Emergency: ₱100,000) and the category behaves like a capped goal — it stops taking a share once full. Leave it blank (Savings, Excess, or any custom "no limit" fund) and it just keeps taking its percentage share forever. That one on/off field is what the three tiers above implement under the hood; nobody needs to know the words "goal," "capped percent," or "remainder" to use the app.

## 2. Auth & sharing model

Two separate Supabase Auth accounts (yours and Ann's), each with its own `household_members` row, both pointing at the same `households.id`. That row is the only place identity and household membership meet — every household-scoped table (`incomes`, `categories`, `bill_items`, `ledger_entries`, `household_invites`) carries a `household_id` column and is scoped by the same RLS predicate:

```sql
using (
  household_id in (
    select household_id
    from household_members
    where user_id = auth.uid()
  )
)
```

Same predicate reused across select/insert/update/delete on every table — the parallel techspec task should pin down the exact SQL and any Supabase-specific gotchas.

**Captain's call — sign-in method:** both email/password and **Google** sign-in. Supabase Auth has Google as a built-in OAuth provider, so this is a config toggle on the Supabase project (redirect URL + a Google Cloud OAuth client), not a separate identity system — whichever method Ann uses to sign up, her `auth.users` row works the same way with `household_members`.

**Onboarding — how Ann joins your household, not her own:**

1. You sign up first — the app creates your `households` row and your `household_members` row automatically on first login.
2. You generate an invite code — a row in `household_invites`, shared with Ann however you like (text, WhatsApp).
3. Ann signs up and redeems it — her sign-up flow has an "enter invite code" step instead of creating a new household, which inserts her `household_members` row against your `household_id`.

## 4. Tech approach

- **Frontend:** Expo (managed workflow) + React Native + TypeScript. Managed workflow means no native Android/iOS project to hand-maintain, and `eas build` produces an installable Android APK/AAB without ejecting.
- **Backend:** `@supabase/supabase-js` against Supabase's free tier — Postgres (§1's tables), Auth (§2's two accounts), Storage (headroom for later, e.g. a receipt photo).
- **Allocation engine:** a Postgres function or Supabase Edge Function that materializes `ledger_entries` for the current/upcoming payday on demand — not a cron job, since nothing needs to run when nobody's looking.
- **Local dev, before a real Supabase project exists:** the Supabase CLI's local stack (`supabase start`) runs Postgres + Auth + Storage in Docker, driven by SQL migrations checked into the repo (`supabase/migrations/*.sql`). A ship task can build and fully test the schema, RLS policies, and allocation engine entirely locally, then `supabase db push` replays the same migrations against the real free-tier project once it exists. A `supabase/seed.sql` preloads the real numbers (₱20,000 on the 5th/20th, ₱9,000 on the 15th/30th) so local dev looks like the real budget from day one.
- **Who does what:**

  - **A future ship task:** the Expo scaffold, migrations + RLS policies, the allocation engine, all v1 screens, and EAS build config. Nothing in this report authorizes that work to start.
- Exact library choices, Supabase free-tier limits in practice, and the precise Android install path (EAS internal distribution vs. Play Store) are being run down in the parallel `taiwan-expenses-techspec` task — check its report alongside this one before a ship task starts.

## 5. Look and feel direction — decided

**Decided: direction B, with all three kept as switchable themes.** This app is for Ann — it should feel like something built together, not a spreadsheet. Three directions were presented (swatches and mockups are in the live Lavish artifact):

- **A — Evolve the original.** Keep the type system (Bricolage Grotesque headings, Public Sans body, IBM Plex Mono numbers) and category palette from `taiwan-fund-planner.html` — it's already good — adapted for touch: bigger tap targets, a card-based dashboard, both avatar colors visible together. Add small celebratory moments (a progress ring filling in, a confetti burst when a goal fund hits its target). Fastest to build, already validated, easiest to extend.
- **B — Couple-themed warm. Chosen as the default.** Softer, warmer palette (terracotta, deep teal, cream) built around the emotional core of the app — a trip you're saving for together. A "countdown to Taiwan" hero motif, a household nickname instead of "Household," room for a shared photo/avatar per partner. More redesign work — new palette and hero treatment, none of the original CSS reused.
- **C — Playful fintech.** Bold gradient accent, oversized friendly numerals, mascot-style icon badges per category, swipeable payday cards — closest to a Cash App / Copilot Money feel. Highest "wow," but needs a custom icon set and more animation work to avoid feeling unfinished.

**Captain's call — theme picker.** Per the captain's note, this isn't either/or: add a **theme picker in Settings** so A, B, and C are all selectable at runtime, not just one baked in at build time. Mechanically cheap — each direction is just a named set of the same CSS custom properties (colors, optionally the font stack) that the whole app already reads from, so "switch theme" is swapping which value set is active and persisting the choice per device. Added to v1 scope as a small Settings screen.
