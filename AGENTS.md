## Supabase backend

Schema/RLS/allocation-engine spec lives in `docs/plan.md` and `docs/techspec.md` (already reviewed/approved); the original algorithm being reproduced is `taiwan-fund-planner.html`'s `allocateProportional`/`fundAllocation` (search that file for the line-number references cited in migration comments).

- Migrations: `supabase/migrations/*.sql`, applied in filename order. Schema → RLS (`private.user_household_ids()` SECURITY DEFINER pattern) → onboarding (signup/invite trigger) → allocation engine (`public.materialize_payday`).
- `household_id` is denormalized onto `bill_items`/`incomes`/`ledger_entries` via BEFORE INSERT triggers (populated from the parent category/member, overwriting whatever the client sent) so every household-scoped table shares one flat RLS predicate.
- `household_members` has deliberately no client insert/update/delete policy — membership is only ever created by the SECURITY DEFINER `handle_new_user` trigger on `auth.users` (direct signup or invite redemption via `raw_user_meta_data->>'invite_code'`). Don't add a naive `user_id = auth.uid()` insert policy here — it would let any signed-in user self-join any household by guessing its id. Self-renames (Settings → Your profile) likewise go through the SECURITY DEFINER `public.update_own_display_name()` RPC (`20260920000001_update_display_name.sql`), not an UPDATE policy — a row-level policy can't stop a member rewriting their own `household_id`.
- Categories CAN be hard-deleted by a household member (`20260916000001_categories_delete.sql`'s DELETE policy) — this reversed an earlier deliberate no-DELETE design (captain's explicit call: cascade away a category's `bill_items`/`ledger_entries` history too, not a gap to guard against). The client (`src/app/(app)/categories/[id].tsx`) is the only thing standing between a tap and permanently losing that history, via a confirmation `Alert` that names what will be lost when the category has existing bills/history.
- `supabase/tests/run.sh` runs the SQL test suite against a **plain local Postgres** (Homebrew `postgresql@16`), not the real `supabase start` Docker stack — this sandbox has no Docker. `supabase/tests/support/stub_auth.sql` stands in for the platform-managed `auth` schema/roles (and now also stubs the `supabase_realtime` publication that a real project pre-provisions — the realtime migration errors without it on plain Postgres). The migrations themselves are ordinary Supabase-CLI SQL and should run unmodified under a real `supabase start`/`db push` once Docker is available. If Docker becomes available, prefer running `supabase test db` against the real stack instead of this stub.
- psql does not interpolate `:'var'` inside `DO $$ ... $$` bodies (dollar-quoted text is opaque to it) — tests pass values in via `\gset`/`\if` at the top level, or have the DO block look values up itself (e.g. via `auth.uid()`).
- The `\if ... \echo 'FAIL: ...' \quit 1 \endif` assertion idiom used across `supabase/tests/*.sql` silently no-ops on this sandbox's psql 16 (`\quit` ignores an exit-code argument and still exits 0) — a soft check can print FAIL and `run.sh` would otherwise still report success. `run.sh` now also greps each test's output for a `^FAIL:` line as a safety net; keep that in place (or convert new assertions to a `raise exception` inside a `DO $$` block, which does propagate a real nonzero exit) if you add more test files.
- A dedicated RLS/household-isolation security audit (2026-09-14) found the actual policies solid: cross-household reads/writes on every scoped table, `household_members` self-join/tamper/delete, `materialize_payday()` called against a foreign household, and malformed/guessed/reused invite codes were all tried directly against the live Supabase project (two disposable accounts, raw REST/Auth API calls) and locally, and none succeeded. Regression coverage for these lives in `supabase/tests/05_rls_security_audit.sql`.
- Every function sets `set search_path = ''`, so any extension-provided function (`gen_random_bytes`, etc.) called inside one must be schema-qualified as `extensions.<fn>` — see `supabase/tests/support/stub_auth.sql` for why the test stub mirrors a real project's `extensions` schema.
- **A migration merged to the repo is not necessarily live** — nothing auto-applies `supabase/migrations/*.sql` to the linked cloud project (no CI, see the manual-APK-release note below for why). `supabase migration list --linked` diffs local vs. remote versions; a bug that passes every local SQL test yet does nothing in the real app is a strong signal to check this before anything else. (Found 2026-09-17: "delete category" silently no-op'd — client code and the RLS policy were both correct, but `20260916000001_categories_delete.sql` had never been pushed. Fixed by `supabase db push`.) Relatedly, two migrations authored on the same day both used version prefix `20260916000001` — the CLI didn't error on push, but a duplicate version is fragile; give same-day migrations distinct suffixes.
- Client mutations that call `.delete()`/`.update()` should request `{ count: 'exact' }` and treat `count === 0` as an error (see `useDeleteCategory` in `src/lib/queries.ts`) — an RLS policy silently filtering out the target row (missing policy, wrong household, stale migration) returns success with zero rows affected, not a Postgrest error, so a bare `if (error) throw error` reports false success.
- **Delete-account** (`supabase/migrations/20260917000001_delete_account.sql`, `public.delete_own_account()`, wired via `src/lib/auth.tsx`'s `deleteAccount()` and the Settings screen's "Danger zone"): deletes the caller's own `auth.users` row directly from a SECURITY DEFINER SQL function — same elevated-privilege pattern as `handle_new_user`/`create_household_invite` — rather than an Edge Function + service-role Admin API call (no Edge Function infra exists in this repo; a SQL function owned by the migration role already has the needed rights over `auth.users` on a real Supabase project, a well-established community pattern for self-serve account deletion). Household data ownership decision: a solo deleter's whole household is destroyed (nothing orphaned); a deleter sharing a household with a partner only loses their own `household_members` row (+ incomes tied to it) — the household and its shared categories/bills/ledger stay for the partner. Two FKs into `auth.users` had no `ON DELETE` action and would otherwise block the delete (`household_invites.created_by` → now cascade, `household_invites.redeemed_by`/`ledger_entries.checked_by` → now set null). Regression coverage (both the solo and shared-household paths) lives in `supabase/tests/06_delete_account.sql`.
- **Bug reports** (`20260919000001_bug_reports.sql`, Settings → "Report a bug", `useSubmitBugReport`): insert-only for clients — no SELECT policy at all, reports are read from the Supabase dashboard (Table editor → `bug_reports`). So the client insert must not chain `.select()` (the RETURNING read would fail RLS). FKs are `on delete set null` so reports survive account deletion.
- **Per-month fund skip** (`public.category_month_skips`, `20260920000003`): the skip is a (category, month) fact, not a ledger flag — a month's later paydays have no `ledger_entries` row yet, and re-materialization rewrites the ones that do. `materialize_payday` mirrors it onto each payday's row as `status = 'skipped'`, `amount 0`; the client only ever writes the table and then re-runs the RPC. It is deliberately not wired into `compute_monthly_fund_totals` — skipping means the checklist stops asking for that money, not that it gets pushed into the other funds — so un-skipping restores the originally planned amount. The table is deliberately absent from `supabase_realtime`: nothing reads it, and partners sync via the `ledger_entries` rows it causes to change.
- **Deleting a bill item** (`useDeleteBillItem`) never hard-deletes one with checked (paid) history: `ledger_entries.bill_item_id` is `on delete set null`, which would strip the history's label and make those rows collide with the fund-row partial unique index `(category_id, payday_date) where bill_item_id is null`. It retires the item via `end_date = yesterday` instead (the detail screen hides retired items) and first deletes the item's unchecked ledger rows, since `materialize_payday` only upserts and never removes a stale pending row.
- **Extra fund deposits** (checklist "left over" card, category "+ Add contribution") are `ledger_entries` rows with `manual = true` (`20260921000010`). They sit outside `ledger_entries_fund_occurrence`'s one-row-per-(category, payday) index and `materialize_payday` never writes them; any new `on conflict` against that index must repeat its `and not manual` predicate or Postgres can't infer it. The checklist's left over is take-home minus every non-skipped row for that payday, deposits included.
- **Household chat delete/clear** (`20260921000030_chat_delete.sql`): members hard-delete only their own `messages` (RLS delete policy); "Clear history" is a per-member `chat_clears.cleared_at` marker applied inside the messages SELECT policy, so the partner's view is untouched. Supabase Realtime can't filter DELETE events (under RLS the old row carries only the PK), so a `household_id=eq.` subscription never sees deletes — `src/lib/realtime.ts` adds an unfiltered messages DELETE listener that refetches only if the id is cached. Other tables' filtered `event: '*'` subscriptions have the same blind spot for partner deletes.
- **Bill/loan payment terms** are just `bill_items.end_date` (= the last due date); `materialize_payday` already skips a bill past it. The UI takes a "number of payments" and converts it via `termEndDate`/`paymentsLeft` in `src/lib/payday.ts` — no separate term column.
- The `goal` rule tier is balance-adaptive (reads actual `checked` ledger totals each call), not a precomputed static multi-month plan like the original HTML — a deliberate generalization so the plan reacts to what was actually saved. `remaining_periods` for a goal counts months up to (not including) the target month, matching the original's "one month of safety margin" framing.

## Frontend (Expo/React Native)

Scaffolded fresh at the repo root (`src/app` = Expo Router routes, `src/components/ui` = design-system primitives, `src/theme`, `src/lib`). Screens/design language come from `docs/plan.md` §3 and the design system export at `/Users/leo/Downloads/Taiwan Fund Planner Design System` (outside this repo) — see that package's `readme.md` for the token/component rationale.

- **Database types are hand-written** (`src/lib/database.types.ts`) — no Docker/local Supabase in this sandbox to run `supabase gen types typescript`. Regenerate that file for real once a local or real project is reachable.
- **Row/Insert/Update in `database.types.ts` must be `type` aliases, not `interface` declarations.** `@supabase/postgrest-js`'s select-query-parser resolves `.select()` projections (even a plain `'*'`) to `never` when a table's Row type is an interface reference — same shape, only `interface` vs `type` differs. Verified against the installed postgrest-js version; if types.ts errors mysteriously come back as `never`, check this first.
- **Theming:** three runtime-switchable themes (`original`/`warm`/`playful`, warm default) live in `src/theme/tokens.ts`, applied via NativeWind's `vars()` in `src/theme/ThemeProvider.tsx`. `var(--x)` strings only resolve through NativeWind's `className` processing — never pass them to a raw RN `style` prop or a third-party native component (e.g. `react-native-svg`); use `useTheme().vars['--x']` (the resolved hex) for those instead.
- **Styling stack is NativeWind v4 + Tailwind v3** (`tailwindcss@^3.4.17`), not gluestack-ui and not Tailwind v4 — `docs/techspec.md`'s version table paired incompatible versions (NativeWind v4 only targets Tailwind v3; gluestack-ui's current major has moved to a v5/NativeWind-v5/Tailwind-v4 preview line). Design-system components (Button, Callout, Checklist*, etc.) are hand-built in `src/components/ui/` rather than pulled from a component library.
- **One-time cross-device triggers** (e.g. `src/components/GoalCelebration.tsx`, mounted once in `src/app/(app)/_layout.tsx` above the `Tabs` navigator so it watches balances regardless of which screen changed them): persist the "already fired" flag as a column on the owning row and claim it with a conditional update (`.eq(id, x).is(flag_column, null).select().maybeSingle()`) before showing anything client-side. A `null` result means another device's client already claimed it a moment earlier — don't show the celebration/effect again. This is the pattern to reuse for any other "fires exactly once when a threshold is crossed" feature; don't derive "already fired" from render-time state alone (was-below-now-at/above without a persisted claim refires on every remount/app-open).
- **Realtime** (`src/lib/realtime.ts`, `useRealtimeSync`) subscribes one Postgres-changes channel per household (household_members/categories/incomes/bill_items/ledger_entries, filtered by `household_id`) and invalidates the matching TanStack Query keys on any event, rather than hand-patching the cache row-by-row — per `docs/techspec.md` §3's decision, keeping the "additive on top of TanStack Query" framing without the per-row reducer complexity it explicitly warned against. **Every table it subscribes to needs a matching `alter publication supabase_realtime add table ...` migration** (`supabase/migrations/20260913000005_realtime.sql` + `20260914000002_realtime_household_members.sql`) — Supabase does not add tables to the realtime publication by default, and a table present in the client `.on(...)` list but missing from the publication fails silently (no error, just no events), so check both lists stay in sync when adding a new subscribed table. Apply via `supabase db push` (needs the CLI linked to the target project) or the dashboard; the anon/publishable key alone can't run migrations.
- **`refetchOnWindowFocus`/the default `refetchOnReconnect`** (`src/lib/query-client.tsx`) are TanStack Query's only path to resync a client after a dropped connection or backgrounded app — Realtime's `postgres_changes` events are a live feed, not a replay log, so anything missed while disconnected is never redelivered and the cache would otherwise stay stale until an unrelated remount. Both defaults are wired to `window`/`navigator` events that don't exist on React Native, so per [TanStack's official RN guide](https://tanstack.com/query/latest/docs/framework/react/react-native), `QueryClientProvider` wires `focusManager` to RN's `AppState` (`change` → `active`) for the foreground/background case, and `onlineManager` to `@react-native-community/netinfo`'s `addEventListener` for the "network drops without backgrounding" case.

Note running it once rewrites `package.json`'s `android`/`ios` scripts from `expo start --android/ios` to `expo run:android/ios` as a prebuild side effect — revert that if not intended. **It only auto-runs `expo prebuild` when the `android/` directory is missing** — if a stale `android/` already exists from an earlier build, it reuses it as-is and silently skips syncing `app.json`/asset changes (JS-only diffs still take effect via the Metro bundle step, but a native-asset change like an app icon swap, `app.json` permissions/config edit, or new native dependency does NOT get picked up). Symptom: `BUILD SUCCESSFUL` in ~30s with almost every Gradle task `UP-TO-DATE` even though source changed — check `android/app/src/main/res/mipmap-*/ic_launcher*.webp` mtimes against your latest commit if a build finishes suspiciously fast. Fix: run `npx expo prebuild --platform android` (regenerates `android/` from current config/assets, safe since it's gitignored/generated) before the release build whenever a task touches `app.json` or native-facing assets.
- **The `preview` EAS profile builds arm64-v8a-only, not a universal APK** — `eas.json`'s `android.gradleCommand` passes `-PreactNativeArchitectures=arm64-v8a` (the flag `android/gradle.properties` itself documents), dropping armeabi-v7a/x86/x86_64 native libs. Measured on this repo: universal ~107.8 MiB vs arm64-only ~45.6 MiB (-57.7%). Reproduce/verify locally by prebuilding (`npx expo prebuild --platform android`) and running `cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` directly — no EAS credentials needed for that local comparison since the release build type signs with the debug keystore (see build.gradle). Only use this profile for install-testing on arm64 devices/emulators (all real Android hardware since ~2017); it will not install on an x86_64 emulator image or an armeabi-v7a device.
- **The newest installable APK is published as a manually-updated GitHub Release, not a CI workflow** — no `.github/workflows` exist and no repo secrets are configured (captain's explicit call: keep this a one-off manual step, not automation, for now). To publish a new build: build the APK (path above), then `gh-axi release create latest --latest <path/to.apk> -t "Latest build" -F notes.md` (first time) for subsequent builds, `gh-axi release upload latest <path/to.apk>` **fails** with `asset under the same name already exists` — `gh-axi`'s `upload` subcommand has no flag to replace an existing asset (confirmed via `gh-axi release upload --help`; there is no `--clobber` on this `gh-axi`, and it does not overwrite by default either, contrary to earlier notes here). Use the real `gh` CLI's `--clobber` for just this replace step instead: `gh release upload latest <path/to.apk> --clobber --repo locodafux/taiwan-expenses` (already authenticated as `locodafux`). Update the release body too (`gh-axi release edit latest --body-file notes.md`) if the APK's build flavor changed (e.g. universal vs. arm64-only) so the notes don't go stale.
- **Google sign-in was removed entirely (2026-09-16, captain's call)** after repeated fix attempts (moving the OAuth redirect handling to a `Linking.addEventListener` at `AuthProvider` mount, adding the missing `auth/callback` route) still couldn't make the deep-link hand-off work reliably for the captain. Don't re-add or re-fix a Google sign-in path without new direction from the captain — email/password is the only sign-in method now. If this ever comes back: the last investigation confirmed both Supabase's Google-provider config and the Google Cloud OAuth client (redirect URI, client ID) were correctly set up (verified live via the Supabase Management API and by curling Supabase's `/auth/v1/authorize` endpoint directly), so the remaining suspects were either the real browser round-trip on-device (untested end-to-end due to Android emulator contention from concurrent sessions) or the Google Cloud OAuth consent screen being stuck in "Testing" publishing mode with a restricted test-user list.
- **In-app update check (`src/lib/appUpdate.ts`, banner in `src/components/UpdateBanner.tsx`) requires `locodafux/taiwan-expenses` to stay a *public* GitHub repo.** It calls the Releases API with a plain unauthenticated `fetch()` (deliberate — an embedded token would be extractable from the APK), which 404s against a private repo. Since the release process reuses a single `latest` tag rather than bumping a version per build, "is this newer" is decided by comparing the APK asset's `updated_at` against the installed package's `lastUpdateTime` (`expo-application`'s `getLastUpdateTimeAsync`) — no locally persisted "seen" state. Don't reintroduce a JS-side "mark installed" step: confirmed on-device (2026-09-19) that Android kills the app process mid-install (`stop ... due to installPackageLI`), and the `ACTION_VIEW` installer intent never returns `RESULT_OK` anyway, so any code after `startActivityAsync` never records a successful update — that, plus fresh installs from the release page having no record at all, made the banner show forever on up-to-date installs. Consequence of the timestamp rule: a device that installed a local build *before* that same APK was uploaded will see the banner once. If you flip repo visibility, GitHub's Fastly edge cache can keep serving the old 404 to some clients for several minutes.

## Frontend testing (Jest + @testing-library/react-native)

Screen/component tests live alongside their screen in `__tests__/` (e.g. `src/app/(app)/__tests__/`, `src/app/(app)/categories/__tests__/`); `src/test/renderWithTheme.tsx` wraps a real `ThemeProvider` for any screen/component that (directly or via `Button`/`ThemeSwitcher`) calls `useTheme()`.

- **`react-native-reanimated` (v4) crashes under plain `jest-expo`** (`Cannot read properties of undefined (reading 'loadUnpackers')`) the moment a NativeWind-styled component combining `className` + a dynamic `style` prop renders (e.g. the color swatches in `categories/add.tsx`) — `react-native-worklets`' native init runs eagerly at import time regardless of Reanimated's own `IS_JEST` gate. Fixed by pointing Jest at the package's own jest resolver (`package.json`'s `jest.resolver: "react-native-worklets/jest/resolver.js"`), which makes it resolve to the non-native build under test. Do **not** also `jest.mock('react-native-reanimated', () => require('react-native-reanimated/mock'))` — that mock's own import chain still pulls in the real native initializers and breaks NativeWind's internal Reanimated-usage-detection helpers a different way.
- **`@testing-library/react-native` v14's `render`, `fireEvent.press`, and `fireEvent.changeText` are all async** — always `await` them (`await render(...)`, `await fireEvent.press(...)`). Skipping the `await` on `fireEvent.press` doesn't error, it just silently no-ops the press in some cases (state update never flushes before the next assertion), which reads as a mysteriously-missing element rather than an obvious failure.
- No `UNSAFE_getByType`/other `UNSAFE_*` queries in this RNTL version — assert on visible text/absence of text instead of reaching for a component-type query.
- Mock `@/lib/queries` per-hook with `jest.requireActual('@/lib/queries')` spread first (keeps `combineQueryState` real) and only override the specific hooks a screen uses — avoids re-deriving its `isError`/`refetch` combining logic in every test file.
