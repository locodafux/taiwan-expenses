## Supabase backend

Schema/RLS/allocation-engine spec lives in `docs/plan.md` and `docs/techspec.md` (already reviewed/approved); the original algorithm being reproduced is `taiwan-fund-planner.html`'s `allocateProportional`/`fundAllocation` (search that file for the line-number references cited in migration comments).

- Migrations: `supabase/migrations/*.sql`, applied in filename order. Schema → RLS (`private.user_household_ids()` SECURITY DEFINER pattern) → onboarding (signup/invite trigger) → allocation engine (`public.materialize_payday`).
- `household_id` is denormalized onto `bill_items`/`incomes`/`ledger_entries` via BEFORE INSERT triggers (populated from the parent category/member, overwriting whatever the client sent) so every household-scoped table shares one flat RLS predicate.
- `household_members` has deliberately no client insert/update/delete policy — membership is only ever created by the SECURITY DEFINER `handle_new_user` trigger on `auth.users` (direct signup or invite redemption via `raw_user_meta_data->>'invite_code'`). Don't add a naive `user_id = auth.uid()` insert policy here — it would let any signed-in user self-join any household by guessing its id.
- `supabase/tests/run.sh` runs the SQL test suite against a **plain local Postgres** (Homebrew `postgresql@16`), not the real `supabase start` Docker stack — this sandbox has no Docker. `supabase/tests/support/stub_auth.sql` stands in for the platform-managed `auth` schema/roles (and now also stubs the `supabase_realtime` publication that a real project pre-provisions — the realtime migration errors without it on plain Postgres). The migrations themselves are ordinary Supabase-CLI SQL and should run unmodified under a real `supabase start`/`db push` once Docker is available. If Docker becomes available, prefer running `supabase test db` against the real stack instead of this stub.
- psql does not interpolate `:'var'` inside `DO $$ ... $$` bodies (dollar-quoted text is opaque to it) — tests pass values in via `\gset`/`\if` at the top level, or have the DO block look values up itself (e.g. via `auth.uid()`).
- The `\if ... \echo 'FAIL: ...' \quit 1 \endif` assertion idiom used across `supabase/tests/*.sql` silently no-ops on this sandbox's psql 16 (`\quit` ignores an exit-code argument and still exits 0) — a soft check can print FAIL and `run.sh` would otherwise still report success. `run.sh` now also greps each test's output for a `^FAIL:` line as a safety net; keep that in place (or convert new assertions to a `raise exception` inside a `DO $$` block, which does propagate a real nonzero exit) if you add more test files.
- A dedicated RLS/household-isolation security audit (2026-09-14) found the actual policies solid: cross-household reads/writes on every scoped table, `household_members` self-join/tamper/delete, `materialize_payday()` called against a foreign household, and malformed/guessed/reused invite codes were all tried directly against the live Supabase project (two disposable accounts, raw REST/Auth API calls) and locally, and none succeeded. Regression coverage for these lives in `supabase/tests/05_rls_security_audit.sql`.
- Every function sets `set search_path = ''`, so any extension-provided function (`gen_random_bytes`, etc.) called inside one must be schema-qualified as `extensions.<fn>` — see `supabase/tests/support/stub_auth.sql` for why the test stub mirrors a real project's `extensions` schema.
- The `goal` rule tier is balance-adaptive (reads actual `checked` ledger totals each call), not a precomputed static multi-month plan like the original HTML — a deliberate generalization so the plan reacts to what was actually saved. `remaining_periods` for a goal counts months up to (not including) the target month, matching the original's "one month of safety margin" framing.

## Frontend (Expo/React Native)

Scaffolded fresh at the repo root (`src/app` = Expo Router routes, `src/components/ui` = design-system primitives, `src/theme`, `src/lib`). Screens/design language come from `docs/plan.md` §3 and the design system export at `/Users/leo/Downloads/Taiwan Fund Planner Design System` (outside this repo) — see that package's `readme.md` for the token/component rationale.

- **Database types are hand-written** (`src/lib/database.types.ts`) — no Docker/local Supabase in this sandbox to run `supabase gen types typescript`. Regenerate that file for real once a local or real project is reachable.
- **Row/Insert/Update in `database.types.ts` must be `type` aliases, not `interface` declarations.** `@supabase/postgrest-js`'s select-query-parser resolves `.select()` projections (even a plain `'*'`) to `never` when a table's Row type is an interface reference — same shape, only `interface` vs `type` differs. Verified against the installed postgrest-js version; if types.ts errors mysteriously come back as `never`, check this first.
- **Theming:** three runtime-switchable themes (`original`/`warm`/`playful`, warm default) live in `src/theme/tokens.ts`, applied via NativeWind's `vars()` in `src/theme/ThemeProvider.tsx`. `var(--x)` strings only resolve through NativeWind's `className` processing — never pass them to a raw RN `style` prop or a third-party native component (e.g. `react-native-svg`); use `useTheme().vars['--x']` (the resolved hex) for those instead.
- **Styling stack is NativeWind v4 + Tailwind v3** (`tailwindcss@^3.4.17`), not gluestack-ui and not Tailwind v4 — `docs/techspec.md`'s version table paired incompatible versions (NativeWind v4 only targets Tailwind v3; gluestack-ui's current major has moved to a v5/NativeWind-v5/Tailwind-v4 preview line). Design-system components (Button, Callout, Checklist*, etc.) are hand-built in `src/components/ui/` rather than pulled from a component library.
- **Realtime** (`src/lib/realtime.ts`, `useRealtimeSync`) subscribes one Postgres-changes channel per household (household_members/categories/incomes/bill_items/ledger_entries, filtered by `household_id`) and invalidates the matching TanStack Query keys on any event, rather than hand-patching the cache row-by-row — per `docs/techspec.md` §3's decision, keeping the "additive on top of TanStack Query" framing without the per-row reducer complexity it explicitly warned against. **Every table it subscribes to needs a matching `alter publication supabase_realtime add table ...` migration** (`supabase/migrations/20260913000005_realtime.sql` + `20260914000002_realtime_household_members.sql`) — Supabase does not add tables to the realtime publication by default, and a table present in the client `.on(...)` list but missing from the publication fails silently (no error, just no events), so check both lists stay in sync when adding a new subscribed table. Apply via `supabase db push` (needs the CLI linked to the target project) or the dashboard; the anon/publishable key alone can't run migrations.
- **`refetchOnWindowFocus`/the default `refetchOnReconnect`** (`src/lib/query-client.tsx`) are TanStack Query's only path to resync a client after a dropped connection or backgrounded app — Realtime's `postgres_changes` events are a live feed, not a replay log, so anything missed while disconnected is never redelivered and the cache would otherwise stay stale until an unrelated remount. Both defaults are wired to `window`/`navigator` events that don't exist on React Native, so per [TanStack's official RN guide](https://tanstack.com/query/latest/docs/framework/react/react-native), `QueryClientProvider` wires `focusManager` to RN's `AppState` (`change` → `active`) for the foreground/background case, and `onlineManager` to `@react-native-community/netinfo`'s `addEventListener` for the "network drops without backgrounding" case.
- **Testing concurrent multi-member use without two emulators:** run `npx expo start --web` (with `app.json`'s `web.output` temporarily set to `"single"` per the entry below — revert before committing) on a spare port, then open one `chrome-devtools-axi` session per simulated household member via `CHROME_DEVTOOLS_AXI_SESSION=<name>` — each session name gets its own isolated browser profile/storage, so each can be signed in as a different account against the same live Supabase project simultaneously (a single shared profile would have all tabs share one auth session). `chrome-devtools-axi emulate --network Offline` / `--network "Fast 4G"` simulates a dropped connection and reconnect for that one session without touching the others.
- **No Docker in this sandbox** — data-layer code is written and typechecked against the real schema/migrations. `.env.example`/`.env.local` document the `EXPO_PUBLIC_SUPABASE_URL`/`_ANON_KEY` vars for whichever project (local `supabase start` stack or a real cloud project) is currently live.
- **Android emulator works in this sandbox** (`~/Library/Android/sdk`, AVD `Pixel_7a`) once its data partition is large enough — the default 6G AVD disk hits `INSTALL_FAILED_INSUFFICIENT_STORAGE` installing Expo Go; bumped to 10G in `~/.android/avd/Pixel_7a.avd/config.ini` (`disk.dataPartition.size`) with `-wipe-data` on relaunch. `npx expo start --android` (use `CI=1`, not `--non-interactive`, to avoid a prompt) then installs Expo Go and bundles/launches the app.
- **A real Supabase cloud project (`taiwan-expenses`, ref `oxnzczubwjoviyddajge`, org `locodafux`) already exists and has all migrations applied** — `supabase link --project-ref oxnzczubwjoviyddajge` then `supabase projects api-keys --project-ref oxnzczubwjoviyddajge` gets the URL/anon key for `.env.local`; no need to provision a new project or run `supabase start`. Full flows (signup, invite/join, categories, incomes, payday materialization, checklist, Realtime cross-session sync) confirmed working end-to-end against it via the Android emulator.
- **Metro's CI mode (`CI=1 npx expo start`) does not reliably pick up source edits via the in-app dev-menu "Reload"** — it can keep serving a stale bundle. If a code change doesn't seem to take effect after Reload, kill the Metro process and the app (`pkill -f "expo start"`, `adb shell am force-stop host.exp.exponent`) and restart with `--clear` before concluding a fix doesn't work.
- Two crewmates running Expo simultaneously on this machine will collide on Metro's default port 8081 (each gets a separate `.treehouse/.../<n>/taiwan-expenses` worktree) — check `lsof -i :8081` and pass `--port <other>` rather than assuming the port is free. They also share the one emulator (`emulator-5554`/`Pixel_7a`): a sibling's `expo start --android` (Expo Go) can grab foreground focus mid-session and show Expo Go's own dev-menu overlay (`host.exp.exponent/.experience.ExperienceActivity`, "This is the developer menu... SDK version") over what looks like your own app. Confirm which package is actually in front with `adb shell dumpsys activity activities | grep topResumedActivity` before treating it as a bug in your build — it isn't one; just `adb shell am start -n <your.package>/.MainActivity` to refocus. A standalone `expo run:android --variant release` install can also get silently uninstalled if another crewmate wipes/reboots the shared emulator; `adb shell pm list packages | grep <package>` confirms, and reinstalling the already-built `android/app/build/outputs/apk/release/app-release.apk` via `adb install` is faster than rebuilding.
- **`npx expo start --web` crashes at request time (`ReferenceError: window is not defined`, from `SupabaseAuthClient.__loadSession`) as shipped, because `app.json`'s `web.output` is `"static"`** — Expo Router's static-output dev server does an SSR pass in Node for every route, and the Supabase client's session bootstrap touches `window`-backed storage during that pass. This reproduces against a real Supabase project, not just something the original UX-review scout's mock avoided. Either temporarily set `web.output` to `"single"` (SPA/client-only rendering) to get a working browser preview — **revert that change before committing**, it's a real behavior switch (disables SSR/static export), not a dev-only flag — or just prefer the Android emulator (`--android`, see above) for real-backend UI verification instead of `--web`.
- Expo Go's own floating "dev-tools" gear button overlays the top-right corner of every screen and can intercept taps meant for the app's own header buttons there (this app's Settings gear and several screens' header "+ Add" sit in that same corner). Dragging it (`adb shell input swipe`) does not reliably relocate it — it snaps back to the same corner regardless of swipe direction/duration. The reliable workaround: `adb shell input keyevent KEYCODE_TAB` shifts RN's focus to the next focusable element (confirm via `uiautomator dump` / `focused="true"`) and `KEYCODE_ENTER` activates it, bypassing the overlay entirely since it's keyboard-driven rather than a raw touch coordinate.
- **Installable Android APK, two paths, both need real Supabase creds baked in explicitly:**
  - `eas build --platform android --profile preview` (`eas.json`, internal distribution + APK not AAB). EAS archives the project for upload respecting `.gitignore`, so `.env.local` (gitignored) is **silently excluded** — the build succeeds but `src/lib/supabase.ts` throws on launch (`FATAL EXCEPTION`, confirmed via emulator `adb logcat` + inspecting the built APK's Hermes bundle: the real URL was absent, only the "Missing EXPO_PUBLIC_SUPABASE_URL" error string was baked in). Fix: register the vars as EAS-hosted env vars (`eas env:create --environment preview --name EXPO_PUBLIC_SUPABASE_URL --value ... --visibility plaintext --non-interactive`, same for the anon key) — EAS injects those into any build (cloud or `--local`) regardless of `.gitignore`. `eas build --local --non-interactive` additionally needs a real Android keystore, since it can't generate one interactively: `credentials.json` (gitignored) + `"credentialsSource": "local"` on the eas.json profile, keystore generated via `keytool -genkeypair`.
  - `npx expo run:android --variant release` (no EAS at all, mirrors `~/Documents/projects/audiobook-mobile-api/mobile`'s approach) prebuilds `android/` and runs Gradle directly from the working tree, so it reads `.env.local` like any local dev command — no separate env var registration needed. Output APK: `android/app/build/outputs/apk/release/app-release.apk`. Note running it once rewrites `package.json`'s `android`/`ios` scripts from `expo start --android/ios` to `expo run:android/ios` as a prebuild side effect — revert that if not intended.
- **The `preview` EAS profile builds arm64-v8a-only, not a universal APK** — `eas.json`'s `android.gradleCommand` passes `-PreactNativeArchitectures=arm64-v8a` (the flag `android/gradle.properties` itself documents), dropping armeabi-v7a/x86/x86_64 native libs. Measured on this repo: universal ~107.8 MiB vs arm64-only ~45.6 MiB (-57.7%). Reproduce/verify locally by prebuilding (`npx expo prebuild --platform android`) and running `cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a` directly — no EAS credentials needed for that local comparison since the release build type signs with the debug keystore (see build.gradle). Only use this profile for install-testing on arm64 devices/emulators (all real Android hardware since ~2017); it will not install on an x86_64 emulator image or an armeabi-v7a device.
- **The newest installable APK is published as a manually-updated GitHub Release, not a CI workflow** — no `.github/workflows` exist and no repo secrets are configured (captain's explicit call: keep this a one-off manual step, not automation, for now). To publish a new build: build the APK (path above), then `gh-axi release create latest --latest <path/to.apk> -t "Latest build" -F notes.md` (first time) or `gh-axi release upload latest <path/to.apk> --clobber` (subsequent builds, replacing the old asset in place under the same `latest` tag/release rather than piling up new releases).
- **Google sign-in's OAuth redirect must be applied via a `Linking.addEventListener('url', ...)` registered once at `AuthProvider` mount (`src/lib/auth.tsx`), never inside the `auth/callback` route itself (`src/app/auth/callback.tsx`).** Expo Router does need a real route at that path — without one the redirect 404s into the default "Unmatched Route" screen on every sign-in, not just intermittently. But `Linking.useURL()`/`getInitialURL()` called *inside* that route misses the very url event that caused Router to navigate there (the hook subscribes after the event already fired), so the route hangs forever on a warm app-resume even though the identical flow works from a cold start. Verified on-device via `adb shell am start -a android.intent.action.VIEW -d '<uri>'` — quote the whole `-d` value for the *remote* shell (e.g. `adb shell "am start ... -d 'scheme://host#frag'"`) or `#`/`&` in the fragment get stripped/backgrounded before the intent is even built.

## Frontend testing (Jest + @testing-library/react-native)

Screen/component tests live alongside their screen in `__tests__/` (e.g. `src/app/(app)/__tests__/`, `src/app/(app)/categories/__tests__/`); `src/test/renderWithTheme.tsx` wraps a real `ThemeProvider` for any screen/component that (directly or via `Button`/`ThemeSwitcher`) calls `useTheme()`.

- **`react-native-reanimated` (v4) crashes under plain `jest-expo`** (`Cannot read properties of undefined (reading 'loadUnpackers')`) the moment a NativeWind-styled component combining `className` + a dynamic `style` prop renders (e.g. the color swatches in `categories/add.tsx`) — `react-native-worklets`' native init runs eagerly at import time regardless of Reanimated's own `IS_JEST` gate. Fixed by pointing Jest at the package's own jest resolver (`package.json`'s `jest.resolver: "react-native-worklets/jest/resolver.js"`), which makes it resolve to the non-native build under test. Do **not** also `jest.mock('react-native-reanimated', () => require('react-native-reanimated/mock'))` — that mock's own import chain still pulls in the real native initializers and breaks NativeWind's internal Reanimated-usage-detection helpers a different way.
- **`@testing-library/react-native` v14's `render`, `fireEvent.press`, and `fireEvent.changeText` are all async** — always `await` them (`await render(...)`, `await fireEvent.press(...)`). Skipping the `await` on `fireEvent.press` doesn't error, it just silently no-ops the press in some cases (state update never flushes before the next assertion), which reads as a mysteriously-missing element rather than an obvious failure.
- No `UNSAFE_getByType`/other `UNSAFE_*` queries in this RNTL version — assert on visible text/absence of text instead of reaching for a component-type query.
- Mock `@/lib/queries` per-hook with `jest.requireActual('@/lib/queries')` spread first (keeps `combineQueryState` real) and only override the specific hooks a screen uses — avoids re-deriving its `isError`/`refetch` combining logic in every test file.
